# Project Brief: Native Vega-Compatible Chart Engine for Kotlin and Android

## 1. Project objective

Build a native Kotlin chart engine for Android that can:

1. Accept Vega-compatible JSON specifications.
2. Execute the required data transformations, scales, signals, layout, and scene generation in Kotlin.
3. Render the resulting scene graph natively through Android Canvas.
4. Support interactive charts without relying on WebView, JavaScript, or an SVG DOM.
5. Export the same scene graph to SVG, PNG, bitmap, and PDF.
6. Provide both a traditional Android `View` API and a Jetpack Compose API.
7. Be testable primarily on the JVM, with Android emulator and physical-device tests for platform-specific behavior.

The initial implementation should prioritize a sound architecture and a useful Vega subset over immediate full compatibility.

## 2. Product definition

The final public API should support usage resembling:

```kotlin
val chart = VegaChartController.fromJson(specJson)

VegaChart(
    controller = chart,
    modifier = Modifier.fillMaxSize()
)
```

For applications using Views:

```kotlin
val chartView = VegaChartView(context)
chartView.setSpec(specJson)
```

For export:

```kotlin
val svg: String = chart.toSvg()
val bitmap: Bitmap = chart.toBitmap(width = 1200, height = 800)
val pdf: ByteArray = chart.toPdf(width = 1200, height = 800)
```

For events:

```kotlin
chart.events.collect { event ->
    when (event) {
        is ChartEvent.MarkClicked -> handleClick(event.datum)
        is ChartEvent.SelectionChanged -> updateSelection(event.selection)
        else -> Unit
    }
}
```

## 3. Scope decisions

### 3.1 Initial input format

The first release should accept compiled Vega specifications.

Do not implement the full Vega-Lite compiler during the initial milestones. Vega-Lite specifications can initially be compiled to Vega by the upstream JavaScript implementation in the test harness or by the application before delivery to the native runtime.

The long-term pipeline is:

```text
Vega-Lite specification
        ↓
Optional native Vega-Lite compiler
        ↓
Vega specification
        ↓
Kotlin runtime and scene compiler
        ↓
Native scene graph
        ↓
Android Canvas / SVG / PDF / bitmap
```

The initial pipeline is:

```text
Vega specification
        ↓
Kotlin runtime and scene compiler
        ↓
Native scene graph
        ↓
Android Canvas / SVG / PDF / bitmap
```

## 4. Core engineering principles

### 4.1 SVG is an output, not the runtime model

The engine must not use SVG elements as its live internal representation.

SVG should be generated by serializing the native scene graph. Interactive rendering should use the scene graph directly.

### 4.2 Keep the core platform-independent

The following systems must be plain Kotlin/JVM code with no Android imports:

- Specification parsing
- Expression execution
- Dataflow
- Transforms
- Scales
- Signals
- Scene graph
- Geometry
- Hit-test index
- SVG generation
- Canonical snapshot serialization

Android classes must only appear in Android-specific modules.

### 4.3 Use one rendering surface per chart

Do not create:

- One `View` per mark
- One Composable per mark
- One `Drawable` per mark
- One accessibility View per mark
- One `RenderNode` per mark

Draw the chart through one custom surface. Android custom Views receive a `Canvas` in `onDraw`, while Compose provides a Canvas and `DrawScope` abstraction for custom graphics.

### 4.4 Use deterministic internal calculations

Use `Double` for:

- Scale calculations
- Transform calculations
- Dataflow values
- Geometry construction
- Scene coordinates
- Path commands
- SVG output

Convert to `Float` only at the Android rendering boundary.

Normalize negative zero and non-finite values before snapshot serialization.

### 4.5 Avoid allocations during drawing

No scene compilation, JSON parsing, data transformation, text layout, path parsing, or large object construction should happen inside `onDraw`.

The drawing method should consume an already compiled scene snapshot.

### 4.6 Correctness before aggressive optimization

Start with deterministic, testable implementations.

Do not add:

- Object pools
- Custom memory allocators
- RenderNode caching
- Raster caches
- GPU backends
- Parallel dataflow

until profiling demonstrates a need.

## 7. Scene graph design

A suitable starting point is:

```kotlin

    val width: Double,
    val height: Double,
    val background: SceneColor?,
    val root: GroupNode,
    val revision: Long

```

```kotlin
sealed interface SceneNode {
    val id: SceneNodeId
    val bounds: RectD
    val transform: Transform2D
    val opacity: Double
    val visible: Boolean
```

```kotlin

data class PathNode(...)
```

## 8. Rendering implementation

### 8.1 Canonical Android renderer

Implement:

```kotlin
class AndroidCanvasSceneRenderer(
    private val textEngine: AndroidTextEngine,
    private val imageResolver: AndroidImageResolver
) {
    fun render(
        scene: Scene,
        canvas: Canvas,
        viewport: RectF,
        pixelScale: Float
    )
}
```

The renderer must:

1. Save Canvas state.
2. Apply the viewport transform.
3. Apply scene and group transforms.
4. Apply clipping.
5. Draw nodes in scene order.
6. Restore Canvas state.
7. Never mutate the scene.

### 8.2 Paint and Path reuse

Maintain reusable renderer-owned instances:

```kotlin
private val fillPaint = Paint(Paint.ANTI_ALIAS_FLAG)
private val strokePaint = Paint(Paint.ANTI_ALIAS_FLAG)
private val textPaint = TextPaint(Paint.ANTI_ALIAS_FLAG)
private val androidPath = Path()
```

Reset all mutable properties before each use.

Do not create a new `Paint`, `Path`, matrix, array, or collection for every mark.

### 8.3 Rendering behavior

Support:

- Fill
- Stroke
- Stroke width
- Stroke caps
- Stroke joins
- Dash arrays
- Opacity
- Blend mode where supported
- Linear gradients
- Radial gradients
- Clip rectangles
- Clip paths
- Nested transforms
- Antialiasing
- Images
- Text alignment and baseline
- Multiline text

### 8.4 Invalidation

The chart controller must expose revisions:

```kotlin
data class ChartSnapshot(
    val scene: Scene,
    val interactionState: InteractionState,
    val revision: Long
)
```

The Android View should call `invalidate()` only when a visible revision changes.

Use `requestLayout()` only when the chart’s preferred size changes. Avoid calling it for hover, tooltip, or selection changes.

## 9. Text engine

Text measurement is part of chart layout, not merely rendering.

Create this platform-neutral interface:

```kotlin
interface TextEngine {
    fun measure(
        text: TextRun,
        constraint: SizeD? = null
    ): TextMetrics

    fun layout(
        text: TextRun,
        constraint: SizeD? = null
    ): TextLayout
}
```

The Android implementation should use:

- `TextPaint`
- `Paint.FontMetrics`
- `StaticLayout` for multiline and wrapped text
- Android font fallback
- Explicit typeface resolution

Cache text layouts using a key containing:

- Text
- Font family
- Font size
- Font weight
- Font style
- Letter spacing
- Line height
- Width constraint
- Locale
- Text direction

Do not use one text system for measurement and another for drawing.

Tests must tolerate small differences between browser Vega and Android text metrics. Structural geometry and numeric layout should use stricter tolerances than glyph bounds.

## 10. Dataflow and runtime behavior

### 10.1 Initial execution model

Begin with a deterministic single-threaded runtime.

All operators should execute in dependency order. Signal changes should invalidate only dependent operators where practical.

The API should expose:

```kotlin
interface DataflowOperator<I, O> {
    val id: OperatorId
    val dependencies: Set<OperatorId>
    fun evaluate(input: I, context: EvaluationContext): O
}
```

### 10.2 Runtime threading

The first implementation may evaluate synchronously.

Before integration with the UI:

- JSON parsing may run off the main thread.
- Large transform evaluation may run off the main thread.
- Scene snapshots must be immutable before publication.
- Android drawing and accessibility updates must occur on the main thread.

Do not mutate a scene while it is being drawn.

Use a controller pattern:

```kotlin
class VegaChartController {
    val state: StateFlow<ChartState>
    val events: Flow<ChartEvent>

    suspend fun setSpec(json: String)
    suspend fun updateData(name: String, changes: DataChanges)
    fun dispatch(event: ChartInputEvent)
}
```

## 11. Interaction system

### 11.1 Platform-neutral events

Define:

```kotlin
sealed interface ChartInputEvent {
    data class PointerEntered(val point: PointD) : ChartInputEvent
    data class PointerMoved(val point: PointD) : ChartInputEvent
    data class PointerExited(val point: PointD?) : ChartInputEvent
    data class PointerDown(
        val point: PointD,
        val pointerId: Long,
        val device: PointerDevice,
        val buttons: Int
    ) : ChartInputEvent
    data class PointerUp(...) : ChartInputEvent
    data class Tap(val point: PointD) : ChartInputEvent
    data class LongPress(val point: PointD) : ChartInputEvent
    data class Pan(
        val delta: VectorD,
        val phase: GesturePhase
    ) : ChartInputEvent
    data class Zoom(
        val scaleFactor: Double,
        val anchor: PointD,
        val phase: GesturePhase
    ) : ChartInputEvent
    data class Key(val key: ChartKey, val modifiers: Modifiers) : ChartInputEvent
}
```

Translate Android inputs from:

- `MotionEvent`
- `GestureDetector`
- `ScaleGestureDetector`
- Mouse hover
- Trackpad or mouse wheel
- Stylus events
- Keyboard events

### 11.2 Hit testing

Start with a correct linear scan for small scenes.

Add an R-tree or quadtree when scenes exceed a configurable threshold.

Hit test in this order:

1. Convert device coordinates to scene coordinates.
2. Query candidate node bounds.
3. Sort candidates by reverse paint order.
4. Perform precise geometry testing.
5. Return the topmost eligible node.

Precise tests:

- Rectangles: rectangle containment
- Symbols: radius or path containment
- Areas: point-in-path
- Lines: distance to polyline with configurable tolerance
- Text: text layout bounds
- Images: rectangle containment

Touch hit targets should use additional tolerance without changing visual bounds.

### 11.3 Event propagation

Support:

- Mark-level events
- Group-level bubbling
- Event consumption
- Signal updates
- Selection updates
- Tooltip updates

Do not expose Android `MotionEvent` objects to the core runtime.

## 12. Accessibility

The chart must expose a semantic tree separate from the drawing tree.

For the View implementation, use virtual accessibility descendants. `ExploreByTouchHelper` is specifically designed for custom Views that visually represent multiple logical items.

Expose:

- Chart title
- Chart description
- Axis names and ranges
- Legend categories
- Individual important marks
- Selected marks
- Annotations
- Available actions

Do not expose hundreds of thousands of marks as individual accessibility nodes.

Use an adaptive strategy:

```text
Small chart:
  expose every mark

Medium chart:
  expose grouped series and navigable important marks

Dense chart:
  expose summary, ranges, extrema, selection and aggregates
```

Required accessibility actions:

- Activate mark
- Move to next or previous meaningful mark
- Increase or decrease selected domain where relevant
- Reset zoom
- Describe current selection

Add accessibility tests for:

- Node labels
- Bounds
- Focus traversal
- Activation
- Selected state
- Disabled state
- Content updates

## 13. Export subsystem

### 13.1 SVG

SVG serialization must be platform-independent and deterministic.

Requirements:

- Stable identifier generation
- Escaped XML text
- Canonical numeric formatting
- Clip paths
- Gradients
- Transforms
- Text
- Embedded or referenced images according to policy
- Optional metadata
- Configurable decimal precision

Default numeric precision should be sufficient to avoid visible geometry loss while keeping files stable.

### 13.2 Bitmap and PNG

Render through the Android Canvas backend into a Bitmap.

Allow callers to specify:

- Logical width
- Logical height
- Pixel scale
- Background
- Bitmap configuration

### 13.3 PDF

Use the Android Canvas backend with an Android PDF Canvas where supported.

Unsupported drawing operations must either:

- Fall back to a compatible representation, or
- Return a structured export warning

Never silently omit a mark.

4. Canonicalize the output.
5. Compare it with Kotlin output.
6. Write readable differences under `build/oracle-diffs`.

## 18. Testing requirements

### 18.1 Unit tests

Every transform, scale, expression operator, and geometry primitive must have isolated tests.

Include tests for:

- Empty data
- Null values

- NaN and infinity
- Negative zero

- Reversed domains

### 18.2 Scene snapshots

Serialize scenes to canonical JSON.

Canonicalization rules:

- Stable object ordering
- Stable node ordering
- Fixed decimal precision
- Normalized negative zero
- Stable generated IDs
- No memory addresses
- No timestamps
- No platform-dependent line endings

A scene snapshot change must be reviewed as an API or rendering change.

### 18.3 SVG golden tests

Compare canonical SVG rather than raw XML.

Normalize:

- Attribute ordering
- Whitespace
- Decimal formatting
- Generated identifiers
- Empty elements
- Transform formatting

Do not automatically update goldens during normal test execution.

Golden updates must require an explicit command:

```bash
./gradlew updateGoldens
```

### 18.4 Differential tests

Every supported Vega feature should have at least one fixture executed by:


Compare:

- Mark count
- Mark types
- Datum identity
- Coordinates
- Bounds
- Scale outputs
- Signal values
- Path commands
- SVG structure

Use exact comparison for discrete values.

Use documented numerical tolerances for floating-point geometry.

Use separate, larger tolerances for text bounds.

## 19. Initial performance targets

Treat these as engineering targets rather than hard compatibility guarantees.

On a representative mid-range physical Android device:

- Static 10,000-mark chart should render within one display frame after scene compilation where possible.
- Panning a precompiled 10,000-mark scene should maintain approximately 60 frames per second.
- Hit testing among 100,000 indexed points should normally complete in under 4 ms.
- A hover or selection update that does not affect layout should not rerun the entire dataflow.
- Drawing should allocate no significant per-frame heap memory after warm-up.
- Scene serialization and rendering must remain deterministic.

When a target is missed, record:

- Fixture
- Device
- Android version
- Build type
- Median
- P90
- P95
- Allocation count
- Trace artifact

## 21. Agent operating rules

The implementing agent must follow these rules.

### Before changing code

1. Read `PROJECT_BRIEF.md`.
2. Read `STATUS.md`.
3. Read `SUPPORTED_FEATURES.md`.
4. Run the smallest relevant existing test.
5. Inspect the corresponding upstream Vega behavior when implementing compatibility logic.

### During implementation

- Work on one clearly scoped feature at a time.
- Keep core modules free of Android dependencies.
- Add tests with the implementation.
- Prefer simple deterministic logic.
- Preserve datum and node identity where possible.
- Do not update goldens merely to make tests pass.
- Do not introduce an NDK dependency.
- Do not add a second rendering backend before the Canvas backend is correct.
- Do not use reflection for expression evaluation.
- Do not silently approximate unsupported features.
- Add structured diagnostics for partial support.
- Avoid global mutable state.
- Avoid singleton caches whose lifetime cannot be controlled.
- Do not perform network access during tests.
- Pin every dependency.

### After each feature

Run:

```bash
./scripts/test-core.sh
./gradlew lint
./gradlew :demo:assembleDebug
```

When platform behavior changed, also run:

```bash
./scripts/test-android.sh
```

When compatibility behavior changed, run:

```bash
./scripts/oracle.sh
```

Update:

- `STATUS.md`
- `SUPPORTED_FEATURES.md`
- Tests
- Relevant documentation

### Commit requirements

Each commit should:

- Build independently
- Include tests
- Avoid unrelated formatting churn
- Explain compatibility decisions
- Mention any intentional divergence from upstream Vega

## 23. Definition of MVP completion

The MVP is complete when all of the following are true:

1. A compiled Vega JSON specification can be loaded without JavaScript.
2. Bar, line, area, scatter and stacked-bar charts render natively.
3. Axes, legends, labels and titles are supported.
4. Basic transforms and scales execute in Kotlin.
5. Tap, hover, tooltip, selection, pan and zoom work.
6. The chart is available through View and Compose APIs.
7. SVG, PNG and PDF export work.
8. TalkBack can describe and navigate representative charts.

11. The chart renders without WebView.

14. All unsupported Vega features produce explicit diagnostics.

## 24. Final architectural direction

The required long-term architecture is:

```text
Pure Kotlin:
  JSON models
  expressions
  dataflow
  transforms
  scales
  signals
  scene graph
  spatial index
  SVG serializer

Android:
  native text measurement
  Android Canvas renderer
  bitmap and PDF output
  View host
  gestures
  pointer input
  accessibility virtual nodes

Compose:
  public wrapper around the canonical Android host

Optional future work:
  native Vega-Lite compiler
  geographic transforms
  advanced layouts
  dense-data GPU backend
  Kotlin Multiplatform core
```

The first implementation must optimize for correctness, deterministic testing, and a clean boundary between the Vega runtime and Android presentation. Performance optimization should follow profiling evidence rather than architectural speculation.
